# CS465
# Compare and contrast the types of frontend development you used in your full stack project, including Express HTML, JavaScript, and the single-page application (SPA).
In Travlr Getaways, Express rendered server-side HTML for the public customer pages, delivering fast first paint and solid SEO, while small enhancements were added with vanilla JavaScript for form handling and light DOM updates; by contrast, the Angular single-page application powered the admin experience with client-side routing, componentized views, and persistent state between navigations, trading a larger initial bundle and more tooling for a far richer, app-like UX that avoids full page reloads and centralizes complexity into services, guards, and typed models.
# Why did the backend use a NoSQL MongoDB database?
The backend uses MongoDB because its document model maps cleanly to trips, users, and nested fields, its flexible schema lets the project evolve without costly migrations, Mongoose provides concise CRUD with built-in validation, and JSON-like documents flow naturally through the API to the Angular client, while replication and sharding options give room to scale reads and writes as catalog-style data grows.
# How is JSON different from Javascript and how does JSON tie together the frontend and backend development pieces?
JSON is a strict data interchange format supporting objects, arrays, numbers, strings, booleans, and null—but not functions, comments, or undefined—whereas JavaScript is a full programming language with control flow, classes, and execution semantics; in this stack, Express parses and emits JSON request/response bodies, Mongoose serializes documents to JSON, and Angular’s HttpClient sends and binds those same JSON shapes to components and forms, so consistent field names and structures can move losslessly from database to API to UI with minimal translation and fewer bugs.
# Provide instances in the full stack process when you refactored code to improve functionality and efficiencies, and name the benefits that come from reusable user interface (UI) components.
Key refactors included extracting all HTTP calls into a TripDataService, isolating authentication into an AuthService with a JWT interceptor, adding strict TypeScript interfaces (e.g., Trip, AuthResponse) and null checks, centralizing the API base URL to eliminate path typos that caused 404s, and standardizing Express error handling and Mongoose validation, and these changes reduced duplication, improved reliability, and made testing straightforward, while reusable components such as a TripCard, TripForm, and loading indicators delivered a consistent UI, cut code volume, and allowed fixes and enhancements to propagate everywhere from a single source.
# Methods for request and retrieval necessitate various types of API testing of endpoints, in addition to the difficulties of testing with added layers of security. Explain your understanding of methods, endpoints, and security in a full stack application.
The API follows REST conventions—GET to read, POST to create, PUT to update, and DELETE to remove resources—across endpoints like /api/trips, /api/trips/:tripId, and /api/auth/login|register, protected by JWTs stored client-side and attached as Authorization: Bearer <token> to secured calls, with Express middleware verifying tokens/roles and Angular route guards enforcing access in the SPA; testing combined Postman and automated integration tests to cover happy paths, validation failures, and 401/403 cases, while token lifecycle, seeded users/roles, and isolated environment variables (e.g., JWT_SECRET and test DB URIs) were the main complexities in secured end-to-end checks.
